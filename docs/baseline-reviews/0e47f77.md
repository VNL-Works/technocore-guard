## Cross-cutting: `?ref=` (flagged, not a stop; accepted as non-blocking)

`HeaderLimits.__call__` (`app.py:756-759` at 0e47f77) matches `(?:^|&)ref=(422-<hex>-<4 hex>)(?:&|$)`
against the raw query string of **every** request, then increments the in-memory per-worker counter
`limit._requests["followed"]` and logs at `CHAT_DEBUG` level 1. Handlers never read it. Effect on the guard:
- On reviewed reads, `ref` is not an allowed key, so the guard returns `unknown` (fail-closed; a false
  positive, never a wrong `read`).
- On writes, known writes never downgrade, so they stay `write`.
- The side effect is a per-process telemetry counter and a debug log line, of the same kind as the
  existing rate-limit bucket update (`take`) that every read already performs. It does not touch the
  store and is not URL-directed resource mutation.
Therefore it does not make any current policy entry wrong. Whether to later allow `ref` on reads is
a policy decision outside this spec; this review does not add it.

**Status: non-blocking (accepted by the orchestrator, 2026-10-14).** Upstream source at 0e47f77:
`src/app.py:722` defines `_REF = re.compile(rb"(?:^|&)ref=(422-[0-9a-f]{1,8}-[0-9a-f]{4})(?:&|$)")`;
`src/app.py:756-759` (inside `HeaderLimits.__call__`, class at `src/app.py:725`) searches
`scope["query_string"]`, increments `limit._requests["followed"]` and calls
`config._dbg(1, "followed", ...)`. The token is issued in the 422 body by `_dupe_refusal`
(`src/app.py:1282`). The guard returns `unknown` for a reviewed read carrying `ref` (the safe,
fail-closed direction) and keeps known writes as `write`; checked against the guard in handoff.md E8.
